# Настраиваемое число потоков решателя

Цель — в ручном режиме запускать Sparrow Studio с заданным числом потоков, включая значения выше трёх. План охватывает новое приложение `sparrow-studio/app` и веб-версию `sparrow-studio/web`. Выводы основаны на статическом разборе исходников и закреплённых зависимостей.

## Текущее поведение

| Уровень | Что делает код |
| --- | --- |
| `app` | `SettingsView.tsx` предлагает `Automatic`, `1`, `2`, `3`. Тип `Threads` и `parseProject()` принимают только эти значения. `parseProject()` проверяет как импортированные файлы, так и проекты из IndexedDB. |
| `web` | `App.tsx` показывает такой же список. Число хранится в состоянии интерфейса текущей вкладки. |
| Координаторы | Оба `solver.worker.ts` получают `undefined` для `Automatic`, выбирают число по `hardwareConcurrency` с потолком 3 и отклоняют ручные значения выше 3. При доступной общей памяти запускают по одному `rayon.worker.ts` на поток. |
| WASM-мост | `solver-runtime.worker.ts` передаёт число в `initThreadPool()` и сообщает фактический размер пула из `thread_count()`. Затем `solver_config()` в `web/wasm/src/lib.rs` ограничивает поиск минимумом из размера пула и настройки пресета. `Standard` использует максимум 3 воркера в каждой фазе, `Fast` — 2 в Exploration и 3 в Compression. |
| Ядро и CLI | `Separator` создаёт `n_workers` экземпляров поиска и выполняет их через Rayon. На WASM используется глобальный пул. Нативный CLI уже принимает `--workers` как `NonZeroUsize` и передаёт число в обе фазы. Импорт геометрии в jagua-rs также может использовать Rayon. |

Если снять только ограничение координатора, пул из восьми потоков сможет инициализироваться, а поиск получит три экземпляра в `Standard` и два или три в `Fast`. `ready.threads` описывает пул. `phase.workers` описывает конфигурацию поиска. Сейчас `useSolver.ts` записывает оба значения в одно поле `actual` по очереди.

Источники в проекте — [настройки app](sparrow-studio/app/src/ui/views/SettingsView.tsx), [разбор проекта](sparrow-studio/app/src/project/file.ts), [настройки web](sparrow-studio/web/src/App.tsx), [координатор](sparrow-studio/web/src/workers/solver.worker.ts), [WASM-мост](sparrow-studio/web/wasm/src/lib.rs), [Separator](sparrow/src/optimizer/separator.rs) и [аргументы CLI](sparrow/cli/src/args.rs).

## Предлагаемое поведение

- **Automatic.** Сохранить значение `0` в проекте и текущий автоматический расчёт с резервом одного логического ядра и максимумом три. В этом режиме сохранить число поисковых воркеров, заданное пресетом.
- **Ручной ввод.** Принимать целое `N` от 1 до технического предела текущей сборки. При успешном запуске использовать пул размера `N` и по `N` поисковых воркеров в Exploration и Compression для обоих пресетов. `hardwareConcurrency` служит для автоматического режима и подсказки в интерфейсе. Ручное значение может его превышать.
- **Ограничения среды.** При отсутствии общей памяти или отказе инициализации пула использовать существующий последовательный запуск и показать запрошенное число, фактический `1` и причину. Ручное число сохраняется для следующей попытки. Ошибки во время уже начавшегося поиска выводить как ошибки этого запуска.

### Граница ручного ввода

Закреплённый `rayon-core 1.13.0` использует 8 бит для счётчиков потоков на 32-битной цели. `rayon::max_num_threads()` для `wasm32` возвращает `255`. Rayon сам уменьшает размер пула до этого предела, а наш JS-координатор создаёт воркеры по исходному запросу, который приходит из `wasm-bindgen-rayon`. Значения выше 255 нужно отклонять до создания пула. Зафиксировать основание для этой границы рядом с общей проверкой и сверять её при обновлении Rayon. Доступное число потоков в конкретном запуске зависит от браузера, устройства и размера проекта.

Общая память WASM ограничена 1 ГиБ. Каждый `SeparatorWorker` клонирует состояние задачи и трекер столкновений. При 500 размещённых деталях одна треугольная матрица из пар `f32` занимает около 1 МБ. При переходе к Compression код переносит `prob` из первого `Separator`, поэтому его оставшиеся поля могут занимать память одновременно с новым набором воркеров. Замеры больших проектов покажут, нужно ли освободить состояние Exploration до выделения памяти под Compression.

Связанные файлы — [Cargo.lock](sparrow-studio/web/wasm/Cargo.lock), [сборка WASM](sparrow-studio/web/scripts/build-wasm.mjs), [помощник Rayon](sparrow-studio/web/scripts/rayon-helpers.js), [переход между фазами](sparrow/src/optimizer/mod.rs) и [матрица столкновений](sparrow/src/quantify/pair_matrix.rs).

## Порядок реализации

1. **Ввод и сохранение.** Заменить списки в обеих версиях на `Automatic` и ручное числовое поле. Переиспользовать одну проверку допустимого целого в поле, `parseProject()` и координаторах. Хранить отдельно текст, который пользователь ещё редактирует, и подтверждённое число. Показать ошибку для пустого ручного значения, дроби, отрицательного числа и числа выше предела. Проверить, что клик Nest из поля применяет корректный ввод и явно сообщает об ошибочном. В `app` сохранить схему проекта v1 и совместимость с `0–3`. В `web` использовать существующее состояние вкладки.
2. **Протокол и пул.** Передавать ручной или автоматический режим отдельным признаком, потому что координатор заменяет `threads` фактическим числом при запуске рантайма. В обоих координаторах валидировать вход до старта воркеров. После `initThreadPool()` сверять `thread_count()` с выбранным для этой попытки числом. Использовать существующий цикл создания пула и его очистку при Stop, завершении и частичном отказе. Сохранить пути запуска без явного числа, включая `web/src/bridge.ts` и предварительную загрузку WASM.
3. **Конфигурация поиска.** Передать признак ручного режима из обоих `solver-runtime.worker.ts` в общий Rust-мост. Для ручного режима выставлять `n_workers` обеих фаз по фактическому `thread_count()`. Для автоматического использовать текущую настройку пресета с учётом размера пула. Изменение относится к браузерному мосту. Нативный CLI уже применяет явное число к обеим фазам.
4. **Статус и обработка отказов.** Хранить отдельно запрошенное число, размер пула и число воркеров фазы. Показывать причину последовательного запуска в интерфейсе `app` и `web`, использовать те же значения в диагностике. Проверить таймауты при холодном старте с 4, 8 и большим числом потоков. Сейчас координатор даёт параллельной попытке 8 секунд и последовательной 6, а `useSolver` ждёт первую фазу до 15 секунд. Согласовать эти сроки по замерам, если параллельная попытка оставляет слишком мало времени для последовательной. Проверить отзывчивость Stop при заполнении большого пула.
5. **Сборка и справка.** Собрать четыре WASM-варианта через `npm run wasm:build` и проверить обе версии Studio. Обновить подсказки и README с диапазоном ручного ввода, правилами `Automatic` и условиями перехода на один поток. Убрать из справки утверждение, что больше трёх потоков всегда бесполезны. Оценивать скорость отдельно от факта использования указанного числа.

## Проверка результата

- В `app/tests/project.test.ts` проверить сериализацию и повторное открытие проекта с `8`, прежние проекты с `0–3` и отказ для дробей, строк, отрицательных чисел и `256`. Отдельно открыть сохранённый в IndexedDB проект после перезагрузки.
- В `web/wasm/src/tests.rs` проверить `Standard` и `Fast` с ручным `8`, автоматические настройки обоих пресетов и последовательный режим. При ручном `8` обе фазы должны получить `n_workers = 8`.
- В браузере с изоляцией запустить через интерфейс `4` и `8`. Проверить размер Rayon-пула, сообщения обеих фаз, работу `Separator` по `#workers` в логах и получение валидной раскладки. Дополнительно проверить `Automatic`, ручной `1`, Stop во время старта и поиска, повторный запуск, Skip to compression и очистку всех воркеров пула.
- Адаптировать существующие Playwright-тесты `web`, которые выбирают потоки через `selectOption`. Проверить отсутствие изоляции, искусственный отказ воркера и threaded-сборку без SIMD на числе выше трёх. Для `app` выполнить отдельный браузерный сценарий, поскольку его CI сейчас запускает Vitest, проверку типов, форматирование и сборку.
- Проверить валидацию `255` и `256` без массового запуска воркеров. На доступной машине измерить старт, Stop и пиковую память на более высоких значениях, например 16 и 32, с малым и большим проектом. Эти замеры определят, нужны ли дополнительные изменения запуска или освобождения памяти.
