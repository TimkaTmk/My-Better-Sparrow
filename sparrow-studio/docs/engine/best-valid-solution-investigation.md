# Почему не появляется `Best valid solution`

**Дата разбора:** 8 ноября 2026 г.  
**Область:** браузерная версия `sparrow-studio/web`, где кнопки называются `Live search` и `Best valid solution`.

## Краткий вывод

Это не похоже на поломку самой вкладки. Кнопка `Best valid solution` включается только после того, как solver передал допустимый кандидат и проверка геометрии вернула `passed`. Кандидат с результатом проверки `failed` всё ещё отправляется в `Live search`, но из списка лучших решений исключается. Поэтому видимая раскладка без красных пересечений может сосуществовать с отключённой вкладкой.

**Самый конкретный подозреваемый для большого набора сложных деталей:** если хотя бы у одного размещаемого типа есть отверстие и установлен зазор больше нуля, worker проверяет точный зазор отдельным TypeScript-проходом. Этот проход ограничен 50 миллионами проверок пар вершин. При превышении лимита проверка возвращает `failed` с текстом `Clearance check exceeded its segment budget...`. Такой результат не попадает в `best`. После неудачной проверки `checkedLength` не меняется, поэтому следующие кандидаты тоже проходят ту же дорогую проверку.

Само число деталей ещё не доказывает, что сработал этот лимит: ветка включается только для деталей с отверстиями, а лимит зазора — только при ненулевом зазоре. Без диагностического архива именно этого запуска нельзя утверждать, что лимит уже сработал. Код, однако, точно допускает описанный симптом; диагностика ниже отличает его от остальных вариантов.

## Как возникает симптом

1. В `web/src/App.tsx` `result` берётся из состояния solver только для текущей ревизии проекта. Кнопка `Best valid solution` отключена, пока `result` отсутствует ([App.tsx](../../web/src/App.tsx#L68), [App.tsx](../../web/src/App.tsx#L430)).
2. Rust/WASM публикует внутренне допустимые раскладки как `candidate`; промежуточные состояния идут как `live` ([lib.rs](../../web/wasm/src/lib.rs#L62)).
3. Для проектов с отверстиями `solver-runtime.worker.ts` применяет к каждому новому кандидату `fitSolverCandidate()` и затем независимо вызывает `validate()` ([solver-runtime.worker.ts](../../web/src/workers/solver-runtime.worker.ts#L34)).
4. Проверка включает число и идентичность всех копий, границы материала, пересечения и минимальный зазор. При ненулевом зазоре парные расстояния между сегментами ограничены бюджетом `50_000_000` ([validate.ts](../../web/src/geometry/validate.ts#L59)).
5. `useSolver.ts` сперва сохраняет пришедший кандидат как последний live-кадр и записывает результат проверки в историю. Если `validation.status === 'failed'`, обработчик выходит до присваивания `r.best` ([useSolver.ts](../../web/src/workers/useSolver.ts#L119)). Поэтому кандидат может быть виден в live-режиме, но не включает `Best valid solution`.

## Почему отсутствие красного цвета не опровергает эту причину

`geometry/live.ts` рисует красным только пересечения контуров между показанными копиями. Эта функция прямо обозначена как отображение, которое не даёт раскладке статус проверки ([live.ts](../../web/src/geometry/live.ts#L7)). В частности, отсутствие красного **не проверяет**:

- соблюдён ли требуемый зазор между непересекающимися деталями;
- находятся ли все копии внутри границ материала;
- присутствуют ли все заказанные копии и допустимы ли их повороты.

Например, между двумя контурами может быть положительный зазор 0,2 мм, красного пересечения не будет, но при настройке зазора 1 мм проверка обоснованно отклонит раскладку.

## Как точно установить причину данного запуска

В интерфейсе `Diagnostics` формирует ZIP с `diagnostics.json`, `solver.log` и файлами для воспроизведения ([App.tsx](../../web/src/App.tsx#L334)). В `diagnostics.json` следует посмотреть `history`:

- `validation: "failed"` и сообщение `Clearance check exceeded its segment budget...` — подтвердится лимит точной проверки;
- `Minimum clearance is ...; requested ...` — проверка завершилась, но фактический зазор меньше настроенного; отсутствие красного ожидаемо;
- ошибка про границу материала, число копий или поворот — причина указана напрямую в `errors`;
- пустая `history` при растущем `liveSnapshots` — solver ещё не выдал кандидата, который его собственный алгоритм считает допустимым. Тогда нужно читать `solver.log` и параметры `run-input`; live-кадр сам по себе не является допустимым кандидатом;
- записи `validation: "passed"` при отсутствии результата противоречат штатному переходу в `best` и указывали бы на несовпадение ревизии/сборки либо отдельный дефект доставки состояния.

Диагностический ZIP содержит документ и геометрию деталей. Его нужно хранить и передавать с тем же вниманием, что и исходный проект.

## Рекомендуемое исправление

### 1. Не превращать лимит вычислений в доказанную геометрическую ошибку

Сейчас превышение бюджета выбрасывает исключение, а `validate()` возвращает `failed`. Это смешивает два разных факта: «геометрия нарушает ограничение» и «проверка не успела доказать корректность». Для исчерпания бюджета нужен отдельный статус «не проверено» (`pending` или `unverified`) и явное сообщение в интерфейсе. Такой кандидат нельзя показывать как уже проверенный, но приложение должно сообщать, почему он пока не допущен, вместо молчаливого ожидания.

### 2. Ускорить точную проверку зазора

Использовать пространственный индекс или BVH по ограничивающим прямоугольникам и рёбрам, а точное расстояние считать только для пар, которые могут нарушить заданный зазор. По возможности переиспользовать геометрию/детектор столкновений из Rust/WASM, чтобы алгоритм проверки совпадал с алгоритмом поиска. Сохранять ранний выход при найденном нарушении зазора.

### 3. Перенести проверку из синхронного callback и не повторять заведомо дорогую работу без контроля

Точная JS-проверка сейчас выполняется непосредственно в callback WASM-решателя. Её следует вынести в отдельный worker с ограниченной очередью и замером времени. Очередь должна приоритизировать кандидатов с меньшей длиной и не накапливать одинаковые/хуже текущего лучшего кандидаты. При этом первый кандидат всё равно должен быть проверен: просто разрешить экспорт или назначить результат «valid» без проверки нельзя.

### 4. Показывать причину во время поиска

При каждом `failed` немедленно обновлять статус и краткую причину (например, «кандидат отклонён: зазор меньше настройки» или «проверка сложной геометрии превысила бюджет»). Счётчик отклонённых кандидатов и последняя ошибка должны оставаться доступны в диагностике. Сейчас причина становится видна только если поиск завершился без `best`, поэтому неограниченный запуск может часами выглядеть как обычный поиск.

### 5. Добавить регрессионное покрытие большого проекта

Добавить сценарий со 100 копиями/типами, сложными контурами, отверстиями и ненулевым зазором: допустимый результат должен в итоге появляться; превышение вычислительного бюджета не должно называться доказанно невалидной геометрией или исчезать без объяснения. Отдельно покрыть случай «пересечений нет, но зазор меньше настройки».

## Итог

Код объясняет, как именно `Live search` может показывать визуально чистую раскладку, а `Best valid solution` оставаться выключенным: live-представление проверяет пересечения для показа, а результат проходит более строгий фильтр и при отказе остаётся только live-кандидатом. Для набора примерно из сотни сложных деталей наиболее подозрительна независимая проверка зазора с бюджетом 50 млн пар рёбер, если в наборе есть отверстия и зазор включён. Архив диагностики подтвердит это одной конкретной ошибкой; если кандидатов вообще нет, причина лежит в поиске/исходных ограничениях, а не в переключателе вкладки.

## Что исправлено после анализа

- В `web/src/geometry/validate.ts` заменён полный попарный перебор сегментов на точный BVH-поиск по ограничивающим прямоугольникам; искусственный лимит 50 млн больше не отклоняет кандидата.
- Валидация solver-кандидата больше не нормализует весь уже нормализованный документ повторно и не запускает квадратичный поиск самопересечений для каждой копии. Жёсткое преобразование сохраняет топологию валидного исходного контура; для результата дополнительно проверяются число вершин и конечность координат.
- Worker записывает длительность проверки в историю диагностики. Если кандидат действительно не проходит проверку, причина теперь показывается в интерфейсе во время работающего поиска.
- `npm run build` успешно собрал четыре WASM-варианта и production bundle; `git diff --check` также прошёл. Автоматические тесты не запускались; фактическая скорость на исходном наборе деталей здесь не измерена.

Следующий шаг для подтверждения — открыть обновлённую браузерную сборку и повторить тот же раскрой. Уже работающая старая вкладка не подхватит новый worker. Если кандидат всё ещё не появится, сообщение проверки будет видно сразу; его вместе с новым архивом `Diagnostics` можно использовать для точечного исправления оставшегося ограничения.
